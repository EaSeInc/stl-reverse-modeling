# Reverse modeling from a mesh

## When to Use / Когда применять

- «сделай такой же, но чтобы можно было менять», «доработай готовую модель», «перестрой по STL»;
- профиль, кронштейн, пластина или корпус есть только сеткой, а нужны параметры;
- раскладка деталей по чужим отверстиям (шайбы, стойки, крепёж под плату, рейку, профиль);
- аналог покупной детали по её STL из библиотеки моделей.

Строить в SolidCraft — `solidcraft-modeling`, сверять его движком — `solidcraft-checking`, печатаемость — `fdm-design-engineer`.

## Главное правило

**Размеры берутся из сетки скриптом, а не из памяти.** У модели нет глаз: «посмотреть сверху и выдавить» она может только по числам, которые получила замером. Типовые размеры из каталогов и статей — не эта деталь: расхождение 0.1–0.5 мм на каждой грани даёт деталь, которая выглядит правильной, но не входит в крепёж и не стыкуется. Живой пример: в сетке профиля паз 6.08 вместо «типовых» 6.2, центральное отверстие Ø4.484 вместо Ø5.

Второе правило: **«совпадает» — это число**, а не впечатление. Отчёт пользователю — таблица замеров и отклонений, а не «вроде норм».

Третье правило: **объём и площади — слепой гейт, приёмка — по расстоянию между поверхностями.** Объём сходится и тогда, когда фича не построена: на гайке-барашке M3 сошлось 99.7 % объёма при 13.9 % поверхности дальше 0.4 мм (среднее 0.169, p95 0.646, максимум 1.187 мм — некруглённый корень крыла: снятый галтелью материал ушёл в наросший рядом, сумма сошлась). `scripts/mesh_compare.py ref.stl mine.stl` отдаёт mean/median/p95/max и координаты худших точек — по ним видно, какая именно фича недостроена.

`--compare` **сам совмещает детали** (главные оси + перебор знаков + ICP): без этого у любого STL из интернета своя система координат и сверка даёт «среднее 6 мм» на верной модели.

Свой venv, а не питон SOMA: в `tools/soma/app` стоит uv-managed окружение, `pip install` там отваливается с exit 1.

- Примитивы (плоскости, цилиндры, гексы) при неясной петле — `pyransac3d`, а не подбор радиуса на глаз.
- Нейросетевой реверс (CAD-Recode, InverseCSG, BrepGen) по бенчмаркам даёт медианный Chamfer порядка 0.2 мм — уровень ручного замера, но требует GPU-стека и отдаёт нечитаемое CSG. Не поднимать.
- «Mesh to BRep» в Fusion и «mesh → solid» в FreeCAD дают обтяжку треугольников тысячами микро-граней, а не параметрические фичи: для правки размеров бесполезно.

### Автоподбор параметров: `scripts/fit_params.py`

Когда модель уже есть, а числа в ней подобраны на глаз, дальше подбирает не человек, а расстояние между поверхностями.

```bash
V=C:/Users/boot8/tools/meshrev/venv/Scripts/python.exe
"$V" <скилл>/scripts/fit_params.py --model model.py --ref ref.stl \
     --params W,D,T --mode both --samples 3000 --maxfev 150 \
     --csv fit.csv --json fit.json [--apply]
```

**Инструмент не знает, что за деталь перед ним.** Числа живут только в файле модели: `--params` берётся из имён `param(...)`, границы — из их `min/max` (нет границ — ±`--margin` от значения, по умолчанию 2 %), допуск мешера — `--mesh-tol`/`--angular-tol` (по умолчанию 0.008 мм / 0.06 рад). Ничего про барашка, гнездо или M3 в коде нет и быть не должно; если в скрипте появляется частное имя или число — оно попало туда из примера, а не из задачи.

Модель подходит в любом из трёх видов: SOMA-скрипт (`param` + `add_part`, см. `templates/soma_part_example.py`), обычный CadQuery с функцией `build()`/`make()`/`model()`, либо переменная модуля `BODY`/`SHAPE`/`PART`/`SOLID`. Всё остальное (производные размеры, фичи, галтели) — обычный код модели.

Читает `param(...)` из файла модели, пишет значения, собирает STL, совмещает с эталоном и минимизирует невязки. `--mode sweep` — покоординатный проход по сетке с параболой по трём точкам (даёт ещё и кривую «параметр → rms», по которой видно, определяется параметр фигурой или нет), `--mode ls` — `least_squares`, `--mode both` — проход и добивка (на синтетике добивка сняла ещё 30 % rms). Без `--apply` рабочий `model.py` не меняется.

**Собирать только с временной копии модели.** Подбор пишет значения параметров в файл на каждой итерации — работая по рабочему `model.py`, он затирает его промежуточными числами (поймано: печатные значения 4.85/5.65/2.35/−2.70 исчезли с диска, а `model.py.bak` к тому моменту уже был снят с затрёртого файла). `Fit` копирует модель в `%TEMP%/fit_model_<pid>.py` и работает по ней.

**`--mode sweep` — разведка, `--mode both` — ответ.** Покоординатный проход сходится линейно: на посторонней детали он шёл 0.667 → 0.049 монотонно, но упёрся в точность сетки (истина на той же метрике даёт 0.0049), потому что каждая пара «поза → проход» отрезает от окна фиксированную долю; уточнение до упора съело бы десятки минут. Финальный `least_squares` от точки минимума делает ту же работу за ~20 сборок: 0.049 → 0.012 по rms и 0.204/0.181 → 0.008/0.007 по W/D. Симптом «параметры ползут к истине, но не доползают» — это не метрика и не совмещение, а срезанная точность режима; смотреть в CSV траекторию, а не только итоговые числа.

**Точная стадия ICP — на выборке, а не на всех точках.** `exact_n=2, step_pts=500`: 500 точных запросов уже дают Kabsch без шума, а полная выборка стоит 3.3 с на совмещение и съедает весь бюджет оценки.

**Тест гейтит числа, а не только код возврата.** `scripts/test_fit_universal.py` — самотест на **посторонней** детали: сам пишет модель из `templates/soma_part_example.py` (пластина с бобышкой не по центру), сам собирает эталон из известных значений, гоняет подбор `--mode both` и падает с кодом 1, если промах параметра больше его допуска (`W`/`D` 0.08, `T` 0.06, `BOSS_D` 0.15 — мелкая фича держится хуже всего), `rms_after` выше потолка, файл модели изменился побайтово (md5) или не собрался второй контракт (`build()`). Текущий результат — **0.008 / 0.007 / 0.001 / 0.106, rms 0.0121, ≈7 мин**; до перевода на `--mode both` было 0.204 / 0.181 / 0.001 / 0.029 при rms 0.049, то есть поиск полз к истине, а не ошибался. Гейт, привязанный к конкретной детали (в проекте гайки — `test_fit_synth.py`, там допуски по именам `HUB_H/NUT_AF/...`), годится только как проектный: в скилле он проверяет скилл, а не инструмент. Без численного гейта тест зелёный даже когда подбор возвращает мусор — проверено на себе.

**Синтетика обязательна и она же ставит потолок точности.** Эталон строится из известных значений, старт берётся из модели, проверяется, на сколько подбор вернул истину. Замер на гайке-барашке (4 параметра, 101 сборка, 670 с): `HUB_H` **0.001 мм**, `NUT_AF` **0.012**, `NUT_DEPTH` **0.019** — и `WING_Y0` **0.12…0.15** при старте в 0.30; после перехода на профилирование позы промахи стали **0.024 / 0.017 / 0.050 / 0.039** мм (rms 0.0149) — все четыре параметра в пределах 0.05 мм. Первая версия с позой, снятой один раз, `WING_Y0` вообще не брала (уезжала на 0.15), и я сначала записал это в «параметр неразличим с жёстким сдвигом» — вывод был неверным: параметр различим, если позе разрешено подстраиваться на каждой точке.

**На реальной детали подбор не заменяет замер формы.** На гайке-барашке с 3600 треугольниками профилирование позы за 359 с дало `HUB_H` 4.844 (печатное 4.85 — верно), `NUT_AF` 5.510 (прямой замер 5.50 — верно), но `NUT_DEPTH` 2.499 (замер 1.75) и `WING_Y0` −1.40 (замер внешних плоскостей −3.00/+3.16). Проверка цены честных значений по той же метрике: `WING_Y0 −3.00` даёт rms 0.302 против 0.130 при −1.40, `NUT_DEPTH 1.75` — 0.184 против 0.130 при 2.50. То есть метрика **предпочитает неправильную геометрию вдвое-втрое уверенно**, потому что форма не та: крыло в модели — плоская плита, в сетке скруглённая, у гнезда не воспроизведён раструб, галтель корня снята. Вывод: подбирать можно только те параметры, чья поверхность в модели и в эталоне одного семейства (плоскость, цилиндр, прямой шестигранник); остальное мерять напрямую (`mesh_report` по сечениям). Признак — если минимум rms сидит на значении, противоречащем прямому замеру, никакой перебор стартов этого не исправит: дело в форме, а не в поиске.

**Допуск мешера мельче шага подбора.** `cq.exporters.export(tolerance=0.02, angularTolerance=0.1)` давал **буквально одинаковый STL** для `WING_Y0` −2.657 и −2.613 (оба 650.0629 мм³): оптимизатор видел ступеньки и стоял. Рабочее: `tolerance=0.008, angularTolerance=0.06` — объём поехал 650.73 → 649.21 монотонно, крыло 1:1.

**Позу профилировать на каждой точке, а не фиксировать.** Это заменило прежнюю схему «снять позу с нуля и заморозить на проход» — та была неправильной. У симметричной детали пара «параметры + поза» имеет две ямы: на синтетике (истина, поза B) даёт rms 0.011, а (фит, поза A) — 0.031, и шевеление позы в окрестности второго положения не помогает (проверено сеткой поворотов ±0.15° и сдвигов ±0.08 мм — ни одного улучшения). Замороженная поза держит поиск в мелкой яме. Поза — мешающий параметр: его надо максимизировать на каждой точке (`realign=True` в `_eval`, флаг `--no-profile` его выключает). Эффект на той же синтетике: `WING_Y0` промах **0.150 → 0.039 мм**, остальные три остались в пределах 0.05, rms 0.029 → 0.015. Цена — сборка + совмещение на каждую точку (8 с вместо 2); проход из 4 параметров × 5 точек × 3 пары идёт 11 минут.

**`rigid_align`: грубо по четырём знакам, тонко по двум лучшим.** Стадии ICP `4.0 → 1.0 → 0.4` мм; тонкая доводка проигравшего кандидата не обгоняет лидера, поэтому дорогая стадия — только двум. Шаг ICP свой, на Kabsch, и это обязательное условие, а не вкусовщина: `trimesh.registration.icp` на таких деталях врёт — сетку, сдвинутую на 2 мм, «совмещает» на 0.78 мм (rms 0.40), а сетку с самой собой на 178.6°. Перебор знаков бесполезен, если шаг уводит позу; свой ICP даёт на тех же проверках 0.009° и rms 0.0037 (это уже шелушение сетки).

**Кандидатов позы ранжировать rms, а не медианой.** Медиана не видит мелкие фичи: на пластине с бобышкой (5 % площади) перевёрнутая поза выигрывала по медиане, хотя бобышка встаёт наизнанку. Ранжирование тем же средним квадратом, что и цель подбора, ставит на место; цена — та же выборка точек.

**Расстояния до поверхности: два режима.** Точные (`trimesh.proximity.closest_point`) — 0.17 мс на точку, для отчёта и для цели подбора; для сотен итераций ICP это стена (2400 точек = 0.47 с). Поэтому внутри ICP — KD-дерево по облаку из 120k точек поверхности (4 мс на 2400 точек), а последние три итерации и финальный счёт — точные. Облако строится один раз на эталон и живёт в `Fit`; на попытку «свой точный поиск через KD по вершинам + проекция на треугольник» не тратить время — на крупных треугольниках он врёт до 6.9 мм и всё равно медленный.

**Признак мелкой ямы — rms, который не бьётся с достижимым.** Если итоговый rms заметно хуже, чем rms в известной хорошей точке с позой, снятой именно там, виновато не пространство параметров, а совмещение. Проверять так: `align_now()` на истинных параметрах и `_eval` на них же — разница покажет цену плохой позы.

## Порядок

1. **Замер.** `python3 scripts/section_probe.py <file.stl> [--slice 0.5] [--tol 0.08] [--through] > probe.json`. Скрипт на numpy, без установок: читает бинарный и ASCII STL, сам находит ось выдавливания (наибольший габарит; с `--through` — наименьший, чтобы сквозные отверстия пластины вышли кругами с координатами), режет сечение, собирает замкнутые контуры, отличает круглые отверстия от контура, отдаёт линии с длинами и углами либо центры и диаметры. Проверять в выводе `contour_closed` и `contour_coverage`: если `false`, контур не является профилем и в `lines` ему верить нельзя.
2. **Гейт призматичности — два замера, а не один.** (а) `deviation_pct` = (площадь сечения × длина − объём сетки) / объём: на настоящей призматической детали выходит 0.0 %. (б) **Профиль площади по 21 срезу вдоль оси**, разброс `(max−min)/mean`: у честной призмы ≤ 1 %, и только этот замер отличает призму от «холма». Объём один врёт: у гайки M3 гейт +1.68 %, а профиль гуляет на 46 % — выше середины убыло ровно столько, сколько ниже прибыло. На полигоне 48 деталей плоский профиль только у 3 записей; у 45 остальных `status_note = "профиль гуляет ±N % — не призма"`. Если сработал только объёмный гейт (0.5–5 %) — это `approx`: габарит и объём верные, форма приблизительная. Так и говорить, а не «почти точная копия».
   Пороги: ≤ 1 % — призма; 1–5 % — почти (кромка скруглена, слои помогут); > 5 % — не призма, стопка или фичеры.
3. **Спека числами.** Контур из `lines` (`from`, `to`, `len`, `angle_deg`) и отверстий (`center`, `diameter`); параметры называются по смыслу (`slot_width`, `boss_d`, `wall`, `bore_d`, `length`), значения — из замера. Упрощение контура держать на `--tol 0.08`: мельче — мусор из триангуляции, крупнее — съедаются фаски. Симметрию проверять по координатам, а не на глаз.
4. **Сборка детерминированным кодом.** Один скрипт, который пересобирает деталь с нуля при каждом запуске и лежит рядом с проектом, — но не по одной команде из чата. Два рабочих пути, оба проверены на живой детали:
   - `scripts/rebuild_prism.py probe.json --length 100 --out out/part` — build123d/OCCT: контур → face → вырез отверстий → extrude, экспорт STEP+STL, сверка с `section_net_area_mm2` в одном проходе. venv на машине Жени: `C:/Users/boot8/AppData/Local/cad/venv` (build123d 0.13.0, ~720 МБ). Другой venv: `uv run --no-project --with build123d python spec.py`.
   - `solidcraft-cli run script.json --out part.step` — без питона вообще, JSON из `{"commands":[{"command":"sketch.create","params":{...}}, ...]}`; скрипт по замеру генерит `scripts/` + параметры (`parameters.add` / `parameters.change {changes:{L:180}}`) → extrude → вырез → `inspect.measure` → `file.export_step`. Готовый генератор: `C:/Users/boot8/AppData/Local/cad/make_sc_script.py`.
   Два ядра (OCCT и SolidCraft) на одном контуре дали объём, совпадающий до 0.0002 % — это и есть независимая проверка: если расходятся, ошибка в спеке, а не в ядре.
   - **Пакет, а не одна деталь:** `scripts/rebuild_suite.py <каталог|файл...> --out-dir out --json-out all.json [--stack 32] [--eps 0.02] [--arcs] [--smart]`. Ось выбирается сам: срез по каждой из трёх осей, кандидат принимается только если сечение + длина закрывают весь bbox (±0.05 мм), затем берётся минимальное отклонение объёма. Вложенность — по чётности охватывающих контуров, поэтому и круги, и шестигранное гнездо гайки, и две рейки в одном теле собираются без ручного разбора. `--arcs` — из того же контура в дуги и прямые (`contour_arcs.py`). `--smart` — строит **и призму, и слои по профилю** (`layers.py`: границы слоёв из ступеней площади, срез каждого слоя подбирается под его долю объёма) и берёт тот вариант, где уход объёма меньше; обе цифры пишутся в `layers_try`. Затем `scripts/summarize.py all.json` → markdown + CSV.
   Итог на 48 деталях (`--arcs --smart`): 3 ok, 21 approx, 24 стопки, 0 падений, медиана |объём| **0.50 %** (было 1.58 % на призмах), ≤1 % — 31 из 48 (было 19), слоями собрано 13 из 48, габарит 0.00 мм у 47 из 48, `mesh_suspect` — 1. Рядом с каждой моделью лежит `part.spec.json` — габарит, длина, площадь, метод сборки, профиль и отверстия с координатами: деталь правится числами, а не пересборкой из меша. STEP сразу читается назад (`import_step`) и сверяется с моделью — `step_vs_model_pct` 0.0000 на всех 48.
5. **Раскладка по таблице.** Позиции крепежа и деталей — CSV/JSON (`x,y,z,rot,parent`), а не вычисления в голове. В коде это цикл `for x, y in holes: Pos(x, y, 0) * washer`; при правке меняется строка таблицы, а не дерево фич. Одна координата, введённая руками, — ошибка, которую потом ищут глазами.
6. **Проверка числами, до экспорта.** (а) тот же гейт `площадь × длина` плюс профиль по срезам для пересобранной модели, расхождение с оригиналом в пределах 0.5 %; (б) bbox каждого тела против таблицы, допуск 0.05 мм; (в) **обратный замер по STEP** — `import_step` и сверка объёма с моделью (`step_vs_model_pct`), а не замер своего же STL: иначе вранья экспорта не видно; (г) `scripts/check_golden.py all.json` — сверка всего прогона с эталоном `suite/golden.json` по статусу, уходу объёма (±0.3 п.п.) и габариту (±0.01 мм). Эталон пишется `--make` и переписывается только осознанно, когда числа улучшились. Ключ сверки — (имя файла, ось), поэтому одно имя из двух семейств схлопывается в один ключ: печатать `записей N → ключей M`, а дубль с разными числами (статус, объём, габарит, объём меша) считать ошибкой и отдавать `exit 1` — иначе двум разным деталям достался один ключ и сверка врёт с уверенным лицом. Саму сверку проверять на заведомо старом прогоне: она обязана найти расхождения, иначе эталон ничего не держит; (д) точное сравнение STEP — `compare_step.py` из `solidcraft-checking`; (е) **нарезка** — `scripts/slice_check.py <part.stl>`: объём не видит ступенек, а слайсер видит. Он схлопывает цепочки `inherits` в пресетах OrcaSlicer (CLI их сам не разрешает) и зовёт `orca-slicer --slice`. На пяти деталях (гайка M3 на 20 слоях, плата на 3, Endstück A на 16, Rail, Verbinder 20) — код 0, ни одной ошибки и предупреждения, gcode на месте. Только после этого STEP в git и STL в OrcaSlicer (`orcaslicer-validation`).
7. **Отчёт.** Габарит, площадь сечения, диаметры и координаты отверстий, отклонение в процентах — таблицей. Пользователь не моделировщик: он описывает задумку словами, а числа — работа агента.

## Правила

- Не просить у пользователя CAD-терминов, эскизов и «правильных» размеров: вход — обычные слова плюс сетка, остальное добывается замером.
- Новый CAD-стек (build123d, CadQuery, FreeCAD) ставить только с согласия: пакет тяжёлый (OpenCASCADE внутри). Сначала показать замер на его же файле, потом предлагать установку.
- **Спека реверса ≠ спека печати.** Посадочные под крепёж повторяют сетку ровно (гнездо гайки M3: AF 5.50), но для FDM в отчёте даются оба числа: печатный размер с зазором (5.65). Напечатанное гнездо теснее из-за усадки и нависаний, и гайка без молотка не садится. Модель собирать с зазором, в отчёте показывать оба.
- **Темп: 3–5 замеров на деталь, дальше отчёт.** Ветка проб, растущая каждый раз, когда неясен следующий шаг, — признак, что нужны не новые пробы, а библиотека и гейт по поверхности. Лишние пробы не улучшают точность, а съедают время пользователя.
- Сетка остаётся справочником. Из STL не получается настоящий solid: отверстия и зазоры в сетке не параметры, а масштабирование меняет их вместе с деталью. Результат — своя параметрическая модель, а не вставленная сетка.
- Правка готовой модели — это правка одного параметра в спеке и перезапуск сборки, не перестройка дерева в GUI.
- Не заявлять «совпадает», «входит», «печатается» без отклонения в процентах или без нарезки.

## Круг, шестигранник, квадрат

**AF мерить расстоянием между плоскостями, а не радиусом вершин.** У гнезда с округлёнными рёбрами на гранях вершин нет вообще: петля из 12 точек состоит из 6 углов и 6 точек скруглений, и любой замер «по радиусам вершин» выдаёт круг Ø6.25 вместо гекса AF 5.50. Правильно: для каждой кромки петли взять расстояние от центра до её прямой (`|n·(mid−c)|`), `AF = 2·min(d)`, `AC = 2·max|вершина|`, отношение `min(d)/max|вершина|` = **0.866** у гекса, **0.707** у квадрата, **1.0** у круга.

**Круг от многоугольника отличать по числу плоскостей, а не по допуску на отношение.** Тесселированное отверстие Ø3.4 — это 12-гранник с ratio 0.966, и по ratio он неотличим от правильного 12-угольника, а по числу различных направлений кромок — 6 против 3 у гекса и 2 у квадрата. Порог: `planes ≥ 5` или ratio > 0.985 — круг.

**Ø круга — медиана радиусов вершин**, плюс вписанный и описанный диаметры отдельно: у 12-гранного отверстия `D_впис` 3.36, `D_опис` 3.42, номинал 3.40, и подставлять в модель крайнее значение нельзя (в первой версии брал максимум и получал Ø3.52 — на 3.5 % больше правды).

**Гнездо под гайку часто не прямой призм.** На том же барашке: дно 2.52, прямая стенка AF 5.50 держится до ~4.45, дальше вход расширяется скруглением до Ø6.3 у верхней плоскости. Кольцо на уровне 4.6 — это уже не гнездо, а его раструб. Фичей считать только кольцо, живущее ≥ 0.4 мм по высоте и не меньше 3 уровней; одиночное кольцо — кромка. Профиль стенки проверять вертикальным резом через ось: `m.section(plane_normal=..., plane_origin=[cx,cy,0])` по плоскости и по углу гнезда.

**Центр кольца в отчёте — в координатах сечения** (`to_2D` переносит плоскость в ноль), а не в координатах файла. Для координат детали либо переводить обратно матрицей из `to_2D()`, либо сразу считать `r` от реальной оси (`cx, cy` ступицы).

**RANSAC — второй голос, не первый.** На барашке `pyransac3d` нашёл ступицу Ø10.60 верно, но проспал сквозное отверстие Ø3.4 и насыпал ложных цилиндров по плоским крыльям: плоскость с большим радиусом кривизны он принимает за цилиндр. Цилиндр брать только с покрытием окружности (доля занятых угловых секторов) и перекрытием по длине.

## Ловушки

- **`net_area` по чётности, а не «минус дырки».** Формула `sum - 2*holes` верна только для двух уровней: на трёх даёт 42 вместо 60 (100 − 49 + 9). Тест на синтетических квадратах это ловит; полигон профилей такую вложенность не содержит (проверено: 0 срезов из 141 меняются), но чужая библиотека может.

- **Объём может совпасть случайно.** У `Winkel D` срез по Z дал гейт +2.385 % (выглядит как «почти призма»), а собранный габарит был на 14.142 мм меньше исходника: сечение не покрывало bbox. Гейт по объёму проверять вместе с габаритом, иначе ложное «почти призма» уезжает в модель.
- **Ось Y зеркалит молча.** `section_probe` отдаёт (u,v) по возрастанию номеров осей — для Y это (X,Z), а `Plane.ZX` в build123d это (x=Z, y=X). `Endstück B` собирался 12×20×40 вместо 40×20×12, и объём при этом сходился, поэтому баг виден только по bbox. Для оси Y координаты контура менять местами.
- **OCCT не пишет STL по не-ASCII пути.** `export_step` создал файл, `export_stl` на `Endstück A.stl` — нет, и упало уже на обратном замере. Имена каталогов вывода — только ASCII.
- **Одинаковые имена из разных папок.** `obj_1_Item C.stl` лежит и в `2020_stls`, и в `2020-V-Slot_stls`; каталог вывода обязан включать родительскую папку, иначе деталь затирается.
- **Стопка слоёв для не-призм.** `--stack N` режет деталь на N срезов и объединяет экструзии: гейт −48 % у `Winkel D` стал +0.49 % (32 слоя), `K_rper_01` −16.6 % → +0.24 %, `Endstück B` −22.5 % → 3.15 %. Ожидать 0.2–3 %, не 0.02 %: контур слоя ограничен триангуляцией меша, шум ~1 %, и больше слоёв не даёт монотонного улучшения (16 → −1.46 %, 32 → +3.15 %, 48 → +1.60 % на одной детали). Цена — сотни граней в STEP и ступеньки на наклонных гранях.
- **Дуги — `ThreePointArc` по трём точкам меша, не по центру.** Центр по МНК врёт на ±0.01 мм, и сторону изгиба приходится угадывать: на `Item C` ошибка раздувала площадь на 30 % и давала дугу 271° вместо 89°. Три точки задают радиус и сторону однозначно; `arc_edge(center, r)` на круглом контуре вообще возвращал `None`.
- **Круг = две дуги.** Замкнутый круг одним ребром OCCT не берёт — резать по точкам `N//4` и `3N//4` (якоря `0` и `N//2` давали плохой стык). Замкнутую ломаную RDP схлопывает в точку — прямые считать по участкам между дугами.
- **Ложная дуга из прямых.** Четыре-пять подряд идущих точек прямоугольника лежат на окружности r≈37 мм с dev≈0, и острые углы срезались дугой на 8.5 мм. Дуга принимается только при 20..359°, среднем шаге точек ≤25° и минимум 8 точках.
- **Самопроверка дуг.** Если площадь по дугам расходится с площадью по хордам больше чем на 1 %, сборка падает обратно на хорды (`arcs_error` в JSON). Дуги всё равно окупаются только на призмах: у стопки 32 сечения на деталь, фит дороже пользы. Итог на полигоне: дуги в 5 деталях из 48, у `Item C` 1 цилиндр → 6, STEP 268 → 192 КБ, объём −0.023 % → −0.004 %.
- **Пресеты OrcaSlicer — дельты, CLI их не ест.** Файлы в `user/default/<вид>/*.json` содержат только отличия плюс `"inherits"`, без `type` — CLI отвечает `unknown config type`, а с `type` — молча `found error, exit`. Нужен цикл по `inherits` до system-пресета и склейка в плоский профиль (это умеет `slice_check.py`). Личный machine-пресет `Flashforge 5X` CLI не принимает и после склейки (в нём `version`, `printer_agent`, `print_host*`), поэтому нарезка идёт на system `Flashforge AD5X 0.4 nozzle`, а процесс и филамент берутся его. Геометрию такой прогон проверяет, калибровку потока — нет.
- **Фаски не восстанавливаются, и это не главная потеря.** Детали в `approx` — не «те же, только с острой кромкой»: у них профиль гуляет на 5–80 %, то есть форма другая при верном объёме. Отдельно про кромку: у платы торцы теряют 4.4 % площади, и это не фаска 45°, а скругление ~0.8 мм плюс зенковка на 4 отверстиях (Ø5.93 у торца против Ø5.48 в середине); `fillet 0.8` объяснил +1.06 %, `chamfer 0.8` — +0.79 %, зенковка — +1.18 %, весь уход 1.28 % ни одна фича не закрывает. Вывод: фичи по кромке не окупаются, реверс-CAD на 1 % двух деталей из 48 — не тот размен.
- **Слои не «всегда точнее» призмы.** `--smart` строит оба варианта: у гайки M3 слои дали 0.43 % против 1.68 %, у платы 0.52 против 1.28, у `Endstück A` 2.02 против 3.45 — а у `Verbinder 40` наоборот 3.96 против 2.35, у `Rail` 8.01 против 0.00. Причина: у Verbinder каждая ступень — скругление, а не полка, и лишние 18 границ добавляют шум триангуляции больше, чем убирают ошибку формы. Решает цифра объёма, а не эвристика «профиль бугристый → слои».
- **Причина `crashed` печатается в строке результата.** Раньше было `{"status": "crashed"}` без текста, и опечатка в пути стоила лишнего прогона. Если ошибки нет в выводе — искать её в `all.json` (`error`), а не гадать.
- **`sys.path.insert(0, ...)` в модулях подсовывает чужие копии.** `rebuild_suite.py` добавлял каталог скриптов скила в начало `sys.path`, и тесты, лежащие в `tests/`, грузили оттуда же старую версию модуля (старая сигнатура `process`, TypeError на ровном месте). Правило: свой каталог — `insert(0)`, чужие/резервные — только `append`.
- **Флаг, заявленный в докстринге, должен разбираться в том виде, в каком заявлен.** `--tol 0.5` двумя аргументами молча оставлял дефолт 0.3: парсер понимал только `--tol=0.5`, а в шапке было написано оба варианта. Неприменившийся допуск выглядит как «сверка прошла». Принимать обе формы и проверять флаг живым прогоном, а не по `--help`.
- **Убитый фоновый прогон может отчитаться `exit 0` и оставить полный на вид JSON.** Не верить уведомлению: сверять на диске число записей в JSON, `files` в саммари и mtime, а перекрытый прогон переименовывать `all6.json.stale` — иначе скрипт, взявший его «последним», покажет другие числа без причины. Лог писать `> all.log 2>&1; echo EXIT $? >> all.log` и ждать по числу строк и хвосту лога (через `read_file`), а не одним `sleep` на весь прогон (полный пакет 48 деталей — около 13 мин).

- **ICP в `trimesh` 5.x тянет масштаб.** `registration.icp` оценивает similarity-преобразование: на гайке-барашке он ужал модель на 1.31 % по каждой оси (det 0.961), объём уехал 650.5 → 625.3 мм³, и отчёт показал «модель на 4 % меньше эталона» там, где модель верная. После ICP вынимать масштаб (`T[:3,:3] /= cbrt(det)`) и возвращать матрицу в SO(3) через SVD; объём в отчёте брать до совмещения, совмещённый показывать отдельно.
- **Сверка без совмещения — не сверка.** Эталон лежал в системе координат файла (габарит 13.75 × 21.02 × 11.02), модель — в канонической (22.83 по главной оси); `closest_point` дал среднее 6.8 мм при верной геометрии. Сначала главные оси + перебор 8 знаков (детерминант +1) по медианному расстоянию, потом ICP.
- **Габарит в файле ≠ габарит по главным осям.** У той же детали bbox файла 13.75 × 21.02 × 11.02, а по осям инерции 10.60 × 11.02 × 22.19 — печатать оба с пометкой, иначе «21 мм» и «22.2 мм» выглядят как расхождение.
- **`write_params` переформатирует файл, если писать все значения подряд.** `read_params` → `write_params` на копии давал `diff` exit 1: неизменённые числа переписывались как `5.2000` вместо `5.2`, и в диффе не видно, что реально изменилось. Правило: значение, отличающееся меньше 1e-12, не трогать — оставлять исходный текст.
- **Автоподбор пишет в файл модели.** Любой фиттер, который меняет параметры и собирает, обязан работать по копии: иначе один прогон стирает рабочие значения, а бэкап снимается уже с затрёртого файла. Проверять после каждого прогона `git status` (или `grep` значений), а не верить, что «он только читал».
- **`np.ptp` вместо метода.** `Q[:,0].ptp()` в numpy 2.x убран, работает только `np.ptp(Q[:,0])`.
- **numpy 2.x:** `np.cross` для двумерных векторов падает с `Both input arrays must be (arrays of) 3-dimensional vectors`. Считать вручную: `ax*by - ay*bx`.
- **Срез ровно по плоскости — нулевая площадь.** Плоскость, попавшая на плоскую грань или ряд вершин, теряет компланарные треугольники: у гаечного профиля сечение читалось `0.00 мм²` при объёме 334 мм³. Скрипт сам перебирает смещения (`0.013`, `0.031`, `0.071`, `0.17` от длины) и берёт первый срез с `contour_coverage = 1.0`; поле `slice_frac` говорит, где он остановился.
- **Знак площади не значит «дырка».** Направление обхода из треугольников не согласовано (SketchUp-экспорт): у гайки два сплошных рельса дали `+14.8` и `−14.8` и в сумме ноль. Считать `net_area`: площадь островов минус контуры, вложенные в них, причём точку «внутри» брать сканированием (`interior_point`), а не центроидом — центроид вогнутого контура лежит снаружи.
- **Дубли контуров.** Совпавшие грани дают один и тот же контур дважды; перед суммированием схлопывать по площади и bbox.
- **`--through` для отверстий.** Срез поперёк длинной оси видит отверстия только если они идут вдоль этой оси. Отверстия в пластине ищутся срезом поперёк её наименьшего габарита: `--through` на плате 18×77×4 дал 4 отверстия Ø5.49 в точках x=128, y=98/118/138/158 — сетка 20 мм, готовая таблица для раскладки шайб. Зенкованные отверстия круглыми не признаются (`r_spread > 2 %`) и в `holes` не попадают — это правильно, диаметр у них переменный.
- **Цифры годны до экспорта.** 48 файлов из библиотеки профилей разложились на 14 призм (|откл.| ≤ 5 %), 22 «почти призмы» (5–15 %) и 12 не-призм; гейт вызывать на каждом файле перед перестройкой, а не выяснять это после первой сборки.
- **Мелкие фаски.** При `--tol 0.08` фаски меньше 0.1 мм исчезают из `lines`; для печати важны от 0.2 мм — проверять `raw_vertices`, если фаска заявлена.
- **Круг или паз.** Отверстие признаётся круглым при `r_spread < 2 %` среднего радиуса и не меньше 8 точек. Иначе это скругление угла или паз, и выдавать по нему диаметр нельзя. Круглое отверстие строится через `Pos(cx, cy) * Circle(r)` (а не `Polyline`), когда `circle_of` даёт `sd < 0.02*r` — иначе Ø4.48 становится 15-угольником.
- **Габарит ≠ деталь.** Ось выдавливания — наибольший размер bbox, но у несимметричной детали контур брать в её середине (`--slice`), иначе попадёшь в выборку или скругление.
- **Многотельная сборка.** Проверять каждое тело отдельно (bbox, объём), а не суммарный bbox: смещение одной шайбы внутри общего габарита не видно.

## Файлы

- `scripts/section_probe.py` — замер сетки, numpy-only.
- `scripts/rebuild_prism.py` — одиночная призма из `probe.json` в build123d.
- `scripts/rebuild_suite.py` — пакет: авто-ось, bbox-гейт, вложенность, стопка, дуги (`--arcs`), профиль сечения и выбор призма/слои (`--smart`), спека `part.spec.json`, обратное чтение STEP, `mesh_suspect`, самопроверка, JSON на деталь.
- `scripts/layers.py` — профиль `A(z)` по 21 срезу, `flatness`, `ramp_ends`, `segments` (границы слоёв), `layer_part` (сборка по слоям).
- `scripts/check_golden.py` — сверка прогона с эталоном `golden.json`: статус, объём ±0.3 п.п., габарит ±0.01 мм; печатает дубли ключей (48 записей → 47 ключей), `--make` переписывает эталон.
- `scripts/contour_arcs.py` — контур → дуги + прямые: `ThreePointArc` по точкам меша, круг режется на две дуги, прямые через RDP.
- `scripts/slice_check.py` — нарезка без GUI: склеивает `inherits` в пресетах OrcaSlicer, зовёт `orca-slicer --slice`, отдаёт ошибки/предупреждения/число слоёв/gcode.
- `scripts/mesh_report.py part.stl [--json out.json] [--compare model.stl --png diff.png] [--ransac] [--levels 1,3,5]` — весь замер одной командой: геометрия, фичи из колец сечений (AF/AC/Ø/поворот/глубина), плоскости, ступеньки, цилиндры, сверка с моделью по расстоянию поверхностей с автосовмещением.
- `scripts/summarize.py` — `all.json` → markdown-таблица + CSV.
- `scripts/test_rebuild_suite.py` — 31 тест числами: 17 быстрых (чистые функции), 14 с реальной геометрией.
- `scripts/fit_params.py --model model.py --ref ref.stl --params A,B --mode sweep` — автоподбор параметров по расстоянию поверхностей: покоординатный `sweep` с кривой «параметр → rms», `least_squares`, профилирование позы на каждой точке, синтетический тест, работа по копии модели.
- `scripts/mesh_compare.py ref.stl mine.stl [--levels 1,3,5,8] [--points 4000] [--pylib <каталог>] [--json out.json]` — сверка двух сеток: объём/герметичность/эйлер/габарит, площади сечений через shapely, расстояние между поверхностями (среднее/медиана/p95/max + худшие точки), код возврата 1 при провале гейта.
- `references/stl-probe.md` — как читать вывод, пороги и рецепт раскладки по таблице.
